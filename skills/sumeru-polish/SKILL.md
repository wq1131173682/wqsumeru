## 一、润色原则

### 核心原则
> **AI 写得越"正确"的部分越要改，写得越"奇怪"的部分越要保留。**

### 禁止项
| 禁止行为 | 原因 |
|----------|------|
| ❌ 去除冗余表述 | 冗余是人工特征 |
| ❌ 精炼用词 | 精炼是 AI 特征 |
| ❌ 节奏收紧 | 人类写作有松弛感 |
| ❌ 精准用词 | 精准是 AI 特征 |
| ❌ 过度优化的具象比喻 | 如强行用比喻解释抽象概念 |
| ❌ 对话"潜台词"优化 | 过度优化是 AI 特征 |
| ❌ 标点规范化 | 允许重复标点、破碎句 |

### 允许项
| 允许行为 | 说明 |
|----------|------|
| ✅ 个人化比喻 | 甚至不精准的具象比喻 |
| ✅ 模糊表达 | 不确定语气、含混表述 |
| ✅ 口头禅/重复/啰嗦 | 保留口语化特征 |
| ✅ 冗余铺垫 | 保留松弛感 |
| ✅ 对话跑题/自我纠正 | 保留自然感 |

### 副词智能清理
> 目标：去除 AI 式副词堆砌，保留个人化副词使用习惯。清理率约 50%，短句豁免。

#### 过滤条件（满足任一即跳过）
| 条件 | 说明 |
|------|------|
| 句子长度 < 5 字 | 短句保留原貌，不做副词处理 |
| 副词为个人化用词 | 如"居然""愣是""偏要"等带情绪色彩的副词 |
| 副词为方言/口语特征 | 如"可""蛮""特"等口语化副词 |
| 副词在对话中 | 对话内的副词优先保留 |

#### AI 式副词识别（需清理的目标）
| 类型 | 示例 | 清理策略 |
|------|------|----------|
| 程度副词堆砌 | "非常地""极其地""特别地" | 删除或降级为"很""挺" |
| 方式副词模板化 | "迅速地""毫不迟疑地""毫不犹豫地" | 删除，让动作自己说话 |
| 强调副词冗余 | "确实""的确""真的"（连续出现时） | 保留 1 个或删除 |
| 时间副词套路化 | "突然""猛然""刹那间"（频繁出现时） | 隔一清一，相邻 3 段内只保留第 1 个 |

#### 清理执行规则
1. **先判断句子长度**：整句（含标点）< 5 字 → 跳过，不处理
2. **识别副词类型**：区分 AI 式 vs 个人化
3. **隔一清一**：对识别出的 AI 式副词，按出现顺序交替保留和删除（第 1 个保留、第 2 个删除、第 3 个保留……），确保最终保留率为 40-60%
4. **清理后检查**：删除副词后句子是否依然通顺，不通顺则恢复该副词
5. **三句限一**：同一副词类型在连续 3 句内仅保留第 1 次出现，后续出现全部删除
6. **对话豁免**：对话内容中的副词一律不处理

#### 示例
| 原文 | 清理后 | 说明 |
|------|--------|------|
| 他非常地快速地跑过去。 | 他飞快地跑过去。 | "非常地""迅速地"→删除，"飞快"是个人化表达 |
| 她轻轻地、慢慢地、小心翼翼地走过去。 | 她小心翼翼地走过去。 | 副词堆砌，保留1个 |
| 他愣是不同意。 | 他愣是不同意。 | "愣是"是个人化副词，保留 |
| 走。 | 走。 | 仅1字，跳过 |
| "你真的要走吗？" | "你真的要走吗？" | 对话内，不处理 |

## 二、润色边界

### 不可改动
- 主线事实、人物关系、战力体系、伏笔状态、章节结尾钩子
- `outlines/chapters.json` 中 `acceptanceCriteria` 已满足的内容
- `creativeGoal`、`emotionalBeat`、`readerMemoryPoint`、`freshnessHook`（只强化，不篡改）

### 必须遵守
- 术语、人物名、地名、组织名、功法名 → `plan.md` 术语表（旧版 `docs/glossary.md` 只读兼容）
- 承接上一章实际结尾（剧情统一门禁，见 `sumeru-rules continuity.md` 剧情统一门禁）

### 发现逻辑硬伤
记录到 `.sumeru/polish/logic-notes.json`，格式：
```json
{
  "chapter": "037",
  "issues": [
    { "type": "power_level", "desc": "主角战力与consistency-rules冲突", "severity": "high" }
  ]
}
```

## 三、润色等级

| 等级 | 保留比例 | 具体操作 | 不改 |
|------|----------|----------|------|
| **轻度** | 80% 以上原文 | 微调不通顺句式；清理 AI 式副词堆砌（隔一清一）；修复明显病句；其余一律不动 | 不重组段落、不加比喻、不调整对话 |
| **中度** | 60% 原文核心表达 | 做轻度全部操作 + 重组松散段落（合并重复信息段落）；强化画面感（增加具体细节）；优化对话节奏（删多余铺垫、加打断）；适当增加个人化比喻（≤3 处/章） | 不变主线事实、不篡改情绪节拍、不改结尾钩子 |
| **深度** | 保留核心情节脉络 | 做中度全部操作 + 逐句打磨语感和节奏；强化情绪张力（动作暗示＞直白交代）；增加具象比喻和留白（≤6 处/章）；调整对话语气，增强性格区分度 | 不改情节走向、不改变人物关系、不新增伏笔 |

## 四、场景类型差异化润色

不同场景类型的润色重点和底线不同。子Agent润色前先识别本节属于何种场景，按对应规则执行：

| 场景类型 | 识别特征 | 润色重点 | 不可触碰 |
|----------|----------|----------|----------|
| **打斗/战斗** | 动作描写、招式名称、攻防转换 | 动作连贯性、招式画面感、节奏张力；删"他快速挥出一拳"式 AI 模板描写 | 战力等级、胜负走向、招式设定 |
| **对话/交锋** | 引号对话、心理交锋、谈判 | 性格区分度（每个人说话方式不同）、自然度（加入打断/停顿/跑题）、潜台词（不直说但让读者感受到） | 人物关系、信息密度（不能删关键信息） |
| **心理/独白** | 人物内心活动、思考、回忆 | 内心矛盾真实感（不只有一种情绪）、递进层次（从模糊到清晰）、克制的表达（不写成作文） | 人物性格底色、认知水平（不能写出超越人物认知的内容） |
| **日常/过渡** | 场景转换、生活细节、闲笔 | 松弛感（保留"废话"和冗余）、生活细节（具体而非概括）、气氛渲染（环境＞情绪直接说明） | 时间线顺序、与前文承接 |
| **高潮/爽点** | 反转、打脸、揭晓、爆发 | 节奏压缩（删多余铺垫）、画面增强（增加具体感官细节）、情绪拉升（动作描写＞形容词堆砌） | 爽点归属（谁打谁的脸）、因果关系、反转逻辑 |

**规则优先级：** 场景类型规则 > 润色等级规则。例如高潮场景遇到"不要节奏收紧"的禁止项，但高潮本身就需要压缩节奏 → 以场景规则为准。

## 五、子Agent调用模板

父Agent通过 Task tool 启动润色子Agent时，使用以下固定 prompt 模板。

### 父Agent context pack 生成规则

每批子Agent启动前，父Agent生成 2 个文件：

**1. 共享上下文 `shared-polish.md`** — 同批次所有子Agent共用，写入：
- Project Brief、Current Volume、Relevant Characters
- 待润色原文（仅章节范围摘要，非全文）
- Creative Strategy（创意目标、情绪节拍）
- 风格标杆（具象标杆，见第九节）
- Batch Summary（非第一批时）
- Output Requirements

**2. 本组任务卡 `cards-{范围}.md`** — 每子Agent独有，仅写入：
- 本组章节号列表
- 润色等级（轻度/中度/深度）
- 场景类型分布提示（如"第010章以打斗为主，第011章以对话为主"）

**文件位置：** `.sumeru/context-packs/shared-polish.md` + `.sumeru/context-packs/cards-{范围}.md`

## 六、按模式润色

| 模式 | 处理方式 |
|------|----------|
| `short/light` | 全文或用户指定片段。父Agent提取片段内的风格特征（用词偏好、句式习惯、对话风格），注入润色指令。无 context pack，无具象标杆。 |
| `medium/standard` | 按章节或小范围（≤3 章）。父Agent读取目标章节 + 前 1 章用于风格衔接，生成最小风格摘要注入子Agent指令。不生成完整 context pack。 |
| `long/full` | 按 context pack 分片润色（≥4 章）。每个子Agent 1-3 章，context pack 含具象标杆和连续性摘要。 |

**单章增强策略：** 单章润色时，父Agent从前 3 章中提取 1 段最优描写和 1 段最优对话作为隐式风格标杆，写入子Agent指令。保障即使没有批量 context pack，子Agent也有风格锚点。

## 七、独立调用自举

1. 定位项目根目录，读取或生成 `.sumeru/project.json`、`.sumeru/status.json`
2. 根据用户指定范围或 `chapters/` 推断要润色的章节
3. 若缺少 review 输出，不阻塞润色，在 `.sumeru/backlog.md` 记录"未经过 review"
4. 若缺少 `plan.md`、旧版 `docs/style-guide.md` 或 `.sumeru/cache/style-brief.md`，生成临时风格摘要
5. 用户提供片段时直接润色片段；指定章节时读取目标章节和最小风格摘要；批量章节才生成 context pack

默认直接产出最终润色版。修改前保留最小备份，不要求用户阅读 diff 或中间稿。

## 八、子Agent并行润色

当润色章节数 > 3 时，自动启用子Agent并行润色。遵循 `sumeru-rules SKILL.md` 第一节：

| 规则 | 说明 |
|------|------|
| 并行上限 | 最多 5 个子Agent |
| 分片约束 | 每个子Agent最多负责 3 个连续章节 |
| 计算公式 | `min(ceil(总章节数 / 3), 5)` |
| 分配策略 | 按章节顺序连续分组（1-3、4-6、7-9...） |

### 父Agent职责
- 生成 context pack（含具象标杆，见第九节）
- 启动子Agent，传入精简 context pack
- 收集子Agent输出，检查完整性、顺序、命名
- 剧情统一校验（承接检查、人物检查、道具检查、时间线检查、伏笔检查）
- 备份原文件到 `.sumeru/polish/original/`（每章仅保留最近1份）
- 写入润色后正文到 `chapters/`
- 更新 `.sumeru/status.json`（章节状态 → `polished`）
- 刷新 continuity cache
- 合并逻辑硬伤记录到 `.sumeru/polish/logic-notes.json`
- 发现 high/critical 逻辑硬伤时，触发轻量反审（调用 `sumeru-review` 的反审模式）

### 子Agent职责
- 只读 context pack，不读取其他文件
- 根据 context pack 执行润色
- 输出纯文本结果 + `<!-- SUMERU_STATUS -->` 状态标记
- 不碰状态文件、不写项目文件

## 九、具象标杆机制

父Agent在每个批次开始时，从已完成章节中提取标杆段落，嵌入 context pack：

### 提取标准
| 标杆类型 | 选择标准 |
|----------|----------|
| 场景描写 | 环境渲染好、有画面感、用词有个人特色 |
| 对话 | 自然流畅、有性格区分、不"太工整" |
| 情绪高潮 | 爽点爆发自然、不套路化 |

### 嵌入格式
```
【风格标杆】
--场景标杆(第003章)--
[原文段落，300字以内]

--对话标杆(第005章)--
[原文段落，300字以内]

--情绪标杆(第008章)--
[原文段落，300字以内]
```

## 十、数据持久化

### 中间数据（`.sumeru/polish/`）

| 文件 | 说明 | 生成条件 |
|------|------|----------|
| `original/*.md` | 原文件备份 | 每次润色前自动备份，每章仅保留最近1份 |
| `diff/` | 润色前后对比 | 仅用户要求时生成 |

| `style-config.json` | 本次润色配置 | 每批次完成后生成 |

## 十一、与其他 Skill 配合

| 方向 | Skill | 关系 |
|------|-------|------|
| 前置 | `sumeru-write` | 提供待润色原文 |
| 前置 | `sumeru-review` | 提供审查问题列表（非阻塞）；润色发现逻辑硬伤时触发轻量反审 |
| 后续 | `sumeru-finalize` | 润色后内容供完稿校验使用 |

> ⚠️ 下游 Skill 不直接调用上游；需返工时输出结构化计划（见 `sumeru-rules protocol.md` 修改边界）。

## 十二、输出格式规范

### 子Agent输出首行状态标记（遵循 `sumeru-rules SKILL.md` 第三节）
```markdown
<!-- SUMERU_STATUS: chapter=037, status=polished, state_diff={}, char_update={}, plot_update={}, batch=002, timestamp=2026-05-24T02:30:00Z -->
```

> `polish` 子Agent的 `state_diff` 通常为空，因为润色不改变剧情事实。如意外发现状态冲突，在 `state_diff` 中标记并记录到 `logic-notes.json`。

### 父Agent输出（quiet 模式）
- 批次开始：`🔧 开始润色第 X-Y 章（中度）`
- 批次完成：`✅ 第 X-Y 章润色完成，共修改 Z 处`
- 发现逻辑硬伤：`⚠️ 第 X 章发现逻辑问题：...（已记录至 logic-notes.json）`
