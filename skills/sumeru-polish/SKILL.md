## 一、润色原则

### 核心原则
> **AI 写得越"正确"的部分越要改，写得越"奇怪"的部分越要保留。**

### 禁止项
| 禁止行为 | 原因 |
|----------|------|
| ❌ 去除冗余表述 | 冗余是人工特征 |
| ❌ 精炼用词 | 精炼是 AI 特征 |
| ❌ 节奏收紧 | 人类写作有松弛感 |
| ❌ 精准用词 | 精准是 AI 特征 |
| ❌ 过度优化的具象比喻 | 如强行用比喻解释抽象概念 |
| ❌ 对话"潜台词"优化 | 过度优化是 AI 特征 |
| ❌ 标点规范化 | 允许重复标点、破碎句 |

### 允许项
| 允许行为 | 说明 |
|----------|------|
| ✅ 个人化比喻 | 甚至不精准的具象比喻 |
| ✅ 模糊表达 | 不确定语气、含混表述 |
| ✅ 口头禅/重复/啰嗦 | 保留口语化特征 |
| ✅ 冗余铺垫 | 保留松弛感 |
| ✅ 对话跑题/自我纠正 | 保留自然感 |

### 副词智能清理
> 目标：去除 AI 式副词堆砌，保留个人化副词使用习惯。清理率约 50%，短句豁免。

#### 过滤条件（满足任一即跳过）
| 条件 | 说明 |
|------|------|
| 句子长度 < 5 字 | 短句保留原貌，不做副词处理 |
| 副词为个人化用词 | 如"居然""愣是""偏要"等带情绪色彩的副词 |
| 副词为方言/口语特征 | 如"可""蛮""特"等口语化副词 |
| 副词在对话中 | 对话内的副词优先保留 |

#### AI 式副词识别（需清理的目标）
| 类型 | 示例 | 清理策略 |
|------|------|----------|
| 程度副词堆砌 | "非常地""极其地""特别地" | 删除或降级为"很""挺" |
| 方式副词模板化 | "迅速地""毫不迟疑地""毫不犹豫地" | 删除，让动作自己说话 |
| 强调副词冗余 | "确实""的确""真的"（连续出现时） | 保留1个或删除 |
| 时间副词套路化 | "突然""猛然""刹那间"（频繁出现时） | 随机保留50% |

#### 清理执行规则
1. **先判断句子长度**：整句（含标点）< 5 字 → 跳过，不处理
2. **识别副词类型**：区分 AI 式 vs 个人化
3. **随机抽取 50%**：对识别出的 AI 式副词，随机保留一半，清理另一半
4. **清理后检查**：删除副词后句子是否依然通顺，不通顺则恢复该副词
5. **对话豁免**：对话内容中的副词一律不处理

#### 示例
| 原文 | 清理后 | 说明 |
|------|--------|------|
| 他非常地快速地跑过去。 | 他飞快地跑过去。 | "非常地""迅速地"→删除，"飞快"是个人化表达 |
| 她轻轻地、慢慢地、小心翼翼地走过去。 | 她小心翼翼地走过去。 | 副词堆砌，保留1个 |
| 他愣是不同意。 | 他愣是不同意。 | "愣是"是个人化副词，保留 |
| 走。 | 走。 | 仅1字，跳过 |
| "你真的要走吗？" | "你真的要走吗？" | 对话内，不处理 |

## 二、润色边界

### 不可改动
- 主线事实、人物关系、战力体系、伏笔状态、章节结尾钩子
- `outlines/chapters.json` 中 `acceptanceCriteria` 已满足的内容
- `creativeGoal`、`emotionalBeat`、`readerMemoryPoint`、`freshnessHook`（只强化，不篡改）

### 必须遵守
- 术语、人物名、地名、组织名、功法名 → `plan.md` 术语表（旧版 `docs/glossary.md` 只读兼容）
- 承接上一章实际结尾（剧情统一门禁，见 `sumeru-rules` 第十一节）

### 发现逻辑硬伤
记录到 `.sumeru/polish/logic-notes.json`，格式：
```json
{
  "chapter": "037",
  "issues": [
    { "type": "power_level", "desc": "主角战力与consistency-rules冲突", "severity": "high" }
  ]
}
```

## 三、润色等级

| 等级 | 说明 | 保留比例 | 适用场景 |
|------|------|----------|----------|
| 轻度 | 句式优化，保留原有用词习惯和冗余 | 80%以上原文 | 用户要求微调 |
| 中度 | 重构段落结构，提升文笔质感 | 60%原文核心表达 | 默认等级 |
| 深度 | 逐字打磨，保留核心情节脉络 | 保留核心情节脉络 | 用户明确要求 |

---

## 四、按模式润色

| 模式 | 处理方式 |
|------|----------|
| `short/light` | 优先润色 `story.md` 全文或用户指定片段 |
| `medium/standard` | 按章节或小范围润色 |
| `long/full` | 按 context pack 分片润色，每个子Agent 1-3 章 |

---

## 五、独立调用自举

1. 定位项目根目录，读取或生成 `.sumeru/project.json`、`.sumeru/status.json`
2. 根据用户指定范围或 `chapters/` 推断要润色的章节
3. 若缺少 review 输出，不阻塞润色，在 `.sumeru/backlog.md` 记录"未经过 review"
4. 若缺少 `plan.md`、旧版 `docs/style-guide.md` 或 `.sumeru/cache/style-brief.md`，生成临时风格摘要
5. 用户提供片段时直接润色片段；指定章节时读取目标章节和最小风格摘要；批量章节才生成 context pack

默认直接产出最终润色版。修改前保留最小备份，不要求用户阅读 diff 或中间稿。

## 六、子Agent并行润色

当润色章节数 > 3 时，自动启用子Agent并行润色。遵循 `sumeru-rules` 第一节：

| 规则 | 说明 |
|------|------|
| 并行上限 | 最多 5 个子Agent |
| 分片约束 | 每个子Agent最多负责 3 个连续章节 |
| 计算公式 | `min(ceil(总章节数 / 3), 5)` |
| 分配策略 | 按章节顺序连续分组（1-3、4-6、7-9...） |

### 父Agent职责
- 生成 context pack（含具象标杆，见第七节）
- 启动子Agent，传入精简 context pack
- 收集子Agent输出，检查完整性、顺序、命名
- 剧情统一校验（承接检查、人物检查、道具检查、时间线检查、伏笔检查）
- 备份原文件到 `.sumeru/polish/original/`（每章仅保留最近1份）
- 写入润色后正文到 `chapters/`
- 更新 `.sumeru/status.json`（章节状态 → `polished`）
- 刷新 continuity cache
- 合并逻辑硬伤记录到 `.sumeru/polish/logic-notes.json`

### 子Agent职责
- 只读 context pack，不读取其他文件
- 根据 context pack 执行润色
- 输出纯文本结果 + `<!-- SUMERU_STATUS -->` 状态标记
- 不碰状态文件、不写项目文件

## 七、具象标杆机制

父Agent在每个批次开始时，从已完成章节中提取标杆段落，嵌入 context pack：

### 提取标准
| 标杆类型 | 选择标准 |
|----------|----------|
| 场景描写 | 环境渲染好、有画面感、用词有个人特色 |
| 对话 | 自然流畅、有性格区分、不"太工整" |
| 情绪高潮 | 爽点爆发自然、不套路化 |

### 嵌入格式
```
【风格标杆】
--场景标杆(第003章)--
[原文段落，300字以内]

--对话标杆(第005章)--
[原文段落，300字以内]

--情绪标杆(第008章)--
[原文段落，300字以内]
```

## 八、数据持久化

### 用户可见输出
润色结果直接替换 `chapters/` 中的原文件，作为最终版本。

### 中间数据（`.sumeru/polish/`）

| 文件 | 说明 | 生成条件 |
|------|------|----------|
| `original/*.md` | 原文件备份 | 每次润色前自动备份，每章仅保留最近1份 |
| `diff/` | 润色前后对比 | 仅用户要求时生成 |
| `summary.json` | 润色统计报告 | 每批次完成后生成 |
| `style-config.json` | 本次润色配置 | 每批次完成后生成 |
| `logic-notes.json` | 发现的剧情逻辑硬伤 | 发现时追加 |

### summary.json 格式
```json
{
  "batch": "001",
  "chapters": ["037", "038", "039"],
  "mode": "medium",
  "level": "中度",
  "totalWordsOriginal": 8500,
  "totalWordsPolished": 8700,
  "changes": {
    "sentenceRestructure": 12,
    "dialogueTweak": 5,
    "metaphorAdd": 3,
    "redundancyRemoved": 0
  },
  "timestamp": "2026-05-24T02:00:00Z"
}
```

## 九、与其他 Skill 配合

| 方向 | Skill | 关系 |
|------|-------|------|
| 前置 | `sumeru-write` | 提供待润色原文 |

> ⚠️ 下游 Skill 不直接调用上游；需返工时输出结构化计划（见 `sumeru-rules` 第九节）。

## 十、输出格式规范

### 子Agent输出首行状态标记（遵循 `sumeru-rules` 第三节）
```markdown
<!-- SUMERU_STATUS: chapter=037, status=polished, state_diff={}, char_update={}, plot_update={}, batch=002, timestamp=2026-05-24T02:30:00Z -->
```

> `polish` 子Agent的 `state_diff` 通常为空，因为润色不改变剧情事实。如意外发现状态冲突，在 `state_diff` 中标记并记录到 `logic-notes.json`。

### 父Agent输出（quiet 模式）
- 批次开始：`🔧 开始润色第 X-Y 章（中度）`
- 批次完成：`✅ 第 X-Y 章润色完成，共修改 Z 处`
- 发现逻辑硬伤：`⚠️ 第 X 章发现逻辑问题：...（已记录至 logic-notes.json）`
